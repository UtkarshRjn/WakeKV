WakeKV Phase 0–1: what the experiments do
WakeKV · research notes · phases 0–1

What these experiments actually do

Before building a system that moves attention heads' cache between GPU and CPU, we have to answer two cheap questions: do heads really change importance mid-generation (gate G0), and can we see a change coming early enough to prefetch (gate G1)? Everything you ran on DSMLP serves one of those two questions.

1 · one instrumented run

Watching every head, one token at a time

A normal generation loop throws attention away the instant it's used. run_phase0.py runs the same greedy loop but pauses at every decode step to note, for each of the model's heads (36 layers × 16 heads = 576 in Qwen2.5-3B): which positions it looked at (top-64), and how much of its attention landed on the needle — the fact we planted. A head "activates" when its strongest look lands inside the needle and the token it copied is the token the model actually emitted.

Press play: amber cells are heads currently retrieving from the needle. Notice most heads sleep most of the time, a couple work constantly, and some wake up late — that last group is the entire reason WakeKV can exist.

step 0 / 36

Memory trick that makes this affordable: the full attention map for a 5,000-token prompt would be gigabytes, so the prompt is prefilled without attention output, and each decode step's map is reduced to top-64 + two scalars immediately. One run logs ~100–200 MB.

2 · three tasks, three stresses

Why NIAH, a math problem, and a wifi password

niah

Needle in a haystack

A UUID hidden in 5,000 tokens of filler; the question comes at the end. The cleanest retrieval signal — but also the most static setting: once found, heads can lock on. If churn shows even here, the premise is strong.

cot

Long chain-of-thought

A reasoning model (R1-Distill-1.5B) thinks for up to 2,048 tokens; the "needle" is the problem statement itself. Measures question-lookback: heads that re-read the problem mid-derivation. The regime where every frozen-role competitor is untested.

multiturn

Late recall

Turn 1 states facts; three unrelated turns pass; the last turn asks for the wifi password. Retrieval heads must wake up after a long quiet stretch — the exact event our system needs to detect.

3 · gate g0 — measuring churn

Four numbers that say "heads move"

analyze_phase0.py reduces each run to a handful of statistics. Two compare which heads are active step to step (adjacent-step Jaccard; activation entropy vs. a static top-20 baseline). Two compare what each head looks at over time (FlexiCache's chance-corrected overlap RCO, and HeteroCache-style drift events against a resettable baseline). Play with both below — churn is how much of a head's top-k gets replaced each step.

step t
step t+1 (amber = replaced)
–Jaccard |A∩B| / |A∪B|
–overlap |A∩B| / min(|A|,|B|)
–RCO — overlap, minus what luck alone would give in this pool

Shrink the pool with churn high: raw overlap barely moves, but RCO falls toward 0 — in a small pool two random sets overlap by luck, and RCO refuses to call that "stability". This correction is what our first shakedown got wrong (and a unit test now pins down).

Your first shakedown run (Qwen2.5-3B, NIAH, 64 steps). The structure — few chronic churners, many occasional shifters — is precisely what a dynamic controller exploits and a frozen classification can't.

4 · from churn to events

What counts as a head "waking up"?

Raw scores flicker. If we called every flicker a wake-up, we'd be chasing noise — the same artifact we criticized in the premise paper's binary metric. So wake_events() uses hysteresis: a head must stay quiet (below a low bar) for several steps, then jump above a high bar. Tune the thresholds and watch which bumps qualify:

Set quiet-steps to 0 and the single-step blips start counting; raise the high bar and real wake-ups vanish. These events become the ground truth that signals are graded against.

5 · gate g1 — seeing wake-ups early

Four candidate alarms, one bar to clear

analyze_phase1.py replays each logged run and asks, for every wake-up: did signal X cross its threshold in the k steps before? That yields precision (how often an alarm was followed by a real wake-up) and recall (how many wake-ups got warned) at each lead time k.

6 · the verdicts

What the gates decide

g0 · premise

Do heads churn on our models?

Pass → the phenomenon replicates outside the paper; Phase 2 (fork FlexiCache, build the online controller) starts on real footing.

Fail → the idea dies for ~10 GPU-hours instead of 3 months; pivot to the small-model study already shaped in the notes.

g1 · early warning

Can any signal warn in time?

Pass → promotions are prefetched; decode never stalls; the paper claims proactive reversibility.

Fail → fallback (plan risk R2): promote reactively and account for the stall honestly — FlexiCache pauses ~1/16 of steps and got into MLSys, so the fallback is survivable.
